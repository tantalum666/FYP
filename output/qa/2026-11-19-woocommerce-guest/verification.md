# WooCommerce guest order and account boundaries

19 November 2026, Hong Kong. The owner asked to start testing with the existing login and asked which platforms require an account. The source baseline was `cc5a8c16`. The [previous Stripe Checkout and Link Checkout receipts](../2026-11-19-test-checkouts/verification.md) were reused. This slice exercised WooCommerce's cart and order lifecycle against the existing, test-only FYP Stripe merchant. It did not deploy a payment function to the normal Alice release.

## Store setup

Self-hosted WordPress and WooCommerce require a local shop administrator. The owner did not have to sign up at WooCommerce.com, buy hosting, or create a guest account to place this order. The isolated store runs WordPress 7.1.5, WooCommerce 11.3.0 and PHP 8.3.36 on a separate, loopback-only Docker/Colima profile. MariaDB has no published port. The first WordPress Playground incarnation loaded the catalog, but its PHP transport failed TLS negotiation with Stripe. The native environment validated HTTPS successfully. The first listener was stopped. [WooCommerce installation](https://woocommerce.com/document/installing-uninstalling-woocommerce/).

The original WooCommerce Stripe Payment Gateway 11.2.0 recognized the test configuration but rejected the dedicated unclaimed Stripe sandbox's temporary key format. Its own gateway reported that the key format check failed and the method was unavailable at checkout. The provider independently recognized the merchant and the test Visa fixture. The local store then used **Payment Plugins for Stripe WooCommerce 4.0.20**, whose documented test mode accepts manually supplied sandbox keys. The two gateways were not activated together. Both vendor distributions were used without changes to their validation or payment code. The resulting cart offered the `stripe_cc` test card method. Keys and sandbox authority remained outside the public repository. [Gateway test connection](https://paymentplugins.com/documentation/stripe/connect-account/) · [plugin listing](https://wordpress.org/plugins/woo-stripe-payment/).

## What was actually paid

The WooCommerce Store API returned a product priced at 1,700 HKD minor units. A guest added two units and checked the cart total of 3,400. The read-only checkout draft initially had order ID zero. The client accepted this documented checkout phase and submitted through the registered gateway once with the expected total and a provider-created sandbox card PaymentMethod. The resulting Woo order was **13**, payment result success and status processing.

A separate WooCommerce server process reopened the order through `wc_get_order`. The shopper ID was zero, the order had a paid timestamp, and the single line had quantity two and total HK$34. The transaction on that order was used to look up the PaymentIntent and Charge separately at Stripe. Both identified test mode and status `succeeded`. The charge was paid, captured and unrefunded, for exactly HK$34, with the test Visa ending 4242. The customer-facing order-received page showed order 13, the two items and their total. The rendered block theme used different markup from the first screenshot selector. The storefront itself worked and the corrected UI readback uses its actual confirmation text. Real spending, fulfillment and ticket issuance were zero. [Sanitized readbacks](receipts.json) · [WooCommerce Checkout API](https://developer.woocommerce.com/docs/apis/store-api/resources-endpoints/checkout/).

## Owner-dependent steps

The official Link CLI checked the private FYP profile and found no consumer authorization. A new device authorization for the existing login requested only `payment_methods.agentic`. It expired without an observed grant. An operator launcher can open a fresh official authorization when the wallet owner is present. The merchant-side Link payment confirmed earlier is separate evidence from Link Agent Wallet issuing a test virtual card to Alice. [Official Link setup](https://docs.link.com/quickstart/overview).

A new travel tester needs a Duffel developer account or access to an existing team's account. The dashboard issues a `duffel_test_` access token in developer test mode. A local hidden-input launcher accepts only a test token and validates it with a read-only request before storing it privately. No FYP Duffel token was available at closeout, and no Duffel order was created. [Account setup](https://duffel.com/docs/guides/getting-started-with-flights) · [test airline](https://duffel.com/docs/api/overview/test-mode).
