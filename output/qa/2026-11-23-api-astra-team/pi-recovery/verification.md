On 23 November 2026 the original Pi’s wake helper failed a readback of the Linux RTC wakealarm interface at **14:52:20 Hong Kong time**. The application was running release `08200201`. The owner confirmed a button press or power reconnection for the **15:16** return. During that boot the installed timer resumed renewing the RTC. The physical cause of the earlier shutdown remains undetermined. [Device and offline receipts](receipts.json)

The old helper persisted two owner candidate timestamps, explicitly cleared the previous alarm, wrote the new absolute deadline, then performed a single read. An empty read mapped to zero. A different future deadline outside the two persisted timestamps would have remained foreign to a subsequent invocation. The old marker alone could not establish which deadline remained in hardware. Linux exposes an RTC alarm once per scheduled wake. The timer can renew it while Linux is executing. Loss of RTC power or failure before a new wake can be programmed can interrupt that sequence. The ordinary account could read the Linux RTC deadline and service journal. Linux reports the alarm time tracked by its RTC core through this sysfs interface. A direct firmware-register read provides a separate observation. On a later verified boot, the authorized read-only operator compared the stored ownership data and the firmware’s GET_RTC_REG response. At 15:44:50 HKT, boot `ef43e8a8` had the opt-in marker and an initialized owner record. The firmware alarm was enabled and agreed with Linux and that record on 15:47:26 HKT, 156 seconds ahead. Its RTC clock was approximately one second behind the OS clock. This establishes the later firmware state; the failed boot’s register value was not retained. ## Maintenance helper

The candidate renews a known owned future deadline with Linux’s in-place, relative `+=` form. It records pending ownership before touching the register, rechecks ownership after the durable state write and stops reading as soon as it observes the intended value. A live ownership record also triggers bounded confirmation of an unexpected initial value. A transient empty or failed read can be followed by two more reads without reapplying the operation. If the replacement is lost and the slot is empty, it attempts to restore the previous verified, still-future deadline with an absolute write. The kernel rejects that write when another alarm already occupies the slot. After a confirmed restoration or retention, the saved ownership list discards the disproved target. An independent writer can subsequently use that same second without being mistaken for the desk. A failed restoration or unknown future deadline remains visible in the private state and journal. Intentional disarm follows the same verification bounds and never rearms an alarm. The kernel sysfs interface offers no cross-process compare-and-swap against an unrelated privileged writer. [Helper](../../../../desk-companion/scripts/pi/auto_wake.py) · [Pi kernel wakealarm interface](https://github.com/raspberrypi/linux/blob/rpi-6.18.y/drivers/rtc/sysfs.c)

Using the incident timestamps and simulated hardware, the installed helper falsely failed after a single transient empty read and left the slot empty when the replacement was truly lost. The candidate accepted the correct later read in the first case and restored the verified 14:54:49 deadline in the second. The actual incident exposed no final register value to distinguish those possibilities. The local suite exercises transient reads, failed writes, foreign-alarm protection, persistent uncertainty, crash recovery, expiry and intentional disarm. Twenty-nine focused policy tests passed on the Mac. The two Linux-only graph tests skipped on macOS. The original RTC service and timer files remained byte-identical. The local Linux VM’s systemd verifier accepted the shipped pair and detected the former ordering cycle when the old timer ordering was substituted. No deliberate shutdown or hardware alarm write was used to verify this candidate.

The investigation read the active project instructions, handoff, current product and Pi decisions, the 16–18 November recovery, wake, supply and cable evidence, and the installed timer/helper contracts. A pinned SSH session supplied bounded journal, unit, kernel, firmware and RTC read-only evidence. Private logs, full boot IDs, credentials and network identifiers remain outside the public report. The maintenance helper was subsequently deployed on the original Pi.


## Approved helper-only rollout

On 23 November at 16:06:18 HKT the approved operator authenticated original boot `a612ce21`, verified the prior helper SHA-256 and active opt-in, and retained a checked copy of that helper for rollback. It atomically installed the approved code from [maintenance commit `ded3ecfd`](https://github.com/tantalum666/FYP/commit/ded3ecfd3566e872dc2292523fb0005c9100fea7). The running application stayed on its independently versioned release `08200201`.

At **16:07:03 HKT**, the guard returned two successful natural systemd invocations. Their PMIC deadlines were **16:09:31** and **16:10:01 HKT**. Each was 180 seconds after that invocation’s RTC reading. For both, the firmware alarm was enabled, the kernel wakealarm and the stored owner deadline matched, and the installed helper’s SHA-256 matched the reviewed file. The existing timer remained in place. The operator issued no shutdown, reboot, timer restart or power configuration request. The SSH relay subsequently became unavailable. The record contains an observation gap. [Complete structured receipt](receipts.json) · [Maintenance PR](https://github.com/tantalum666/FYP/pull/149)

A new pinned session independently checked the original device again at **21:12:41 HKT** on boot `a98fb674`. The helper and retained backup still matched their new and original full hashes. The two unit files matched their original hashes, both were enabled, the timer was active and the last oneshot returned zero. The PMIC reported an enabled alarm for **21:15:23**, 162 seconds ahead, exactly matching Linux and the persisted owner state. The normal application API served `08200201`, the configured CPU ceiling was 2.4 GHz and the firmware retained `POWER_OFF_ON_HALT=0`.

The first combined check after reconnect did not pass; it did not retain which individual comparison failed. The separately saved full read above passed every comparison. This boot’s first two successful renewals, at uptimes 4.723 and 34.786 seconds, read the RTC at 16 and 46 seconds after the Unix epoch. Later renewals used the correct 2026 calendar time. That establishes loss of valid calendar time on this later boot, without identifying what triggered it or the earlier 14:52 interruption. The helper survived another actual boot. Unattended recovery from a future power interruption and continuous electrical stability remain open.


The same authenticated connection returned 110 read-only acknowledgements over **18 minutes 32 seconds** after the cross-boot session opened at 21:11:12 HKT. Its local observation deadline ended the connection at 21:29:45. This interval measures original-device reachability. Voltage and temperature were not sampled continuously during it.
