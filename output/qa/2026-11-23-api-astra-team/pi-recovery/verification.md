# Original Raspberry Pi power interruption and RTC renewal

On 23 November 2026 the original Pi’s wake helper failed a readback of the Linux RTC wakealarm interface at **14:52:20 Hong Kong time**. The application was running release `08200201`. The owner confirmed a button press or power reconnection for the **15:16** return. During that boot the installed timer resumed renewing the RTC. The physical cause of the earlier shutdown remains undetermined. [Device and offline receipts](receipts.json)

The old helper persisted two owner candidate timestamps, explicitly cleared the previous alarm, wrote the new absolute deadline, then performed a single read. An empty read mapped to zero. A different future deadline outside the two persisted timestamps would have remained foreign to a subsequent invocation. The old marker alone could not establish which deadline remained in hardware. Linux exposes an RTC alarm once per scheduled wake. The timer can renew it while Linux is executing. Loss of RTC power or failure before a new wake can be programmed can interrupt that sequence. The ordinary account could read the Linux RTC deadline and service journal. Linux reports the alarm time tracked by its RTC core through this sysfs interface. A direct firmware-register read provides a separate observation. The privileged ownership file is a separate measurement. [Installed policy](../../../../desk-companion/docs/pi-power-recovery.md) · [Raspberry Pi RTC guidance](https://www.raspberrypi.com/documentation/computers/raspberry-pi.html#real-time-clock-rtc)

At 15:19 the board reported 4.85348 V, 54.9 °C and `0x50000`, recording earlier undervoltage and throttling with no current bits set in that sample. The supply advertised 3,000 mA. The readback showed a 2.4 GHz configured CPU ceiling, a 60-second running Linux watchdog with boot status 0, zero USB/SD boot-overcurrent flags, four USB root hubs and no recognised UPS or HAT. The inspected journals contained no power-key, explicit orderly poweroff, critical-temperature poweroff, kernel-panic or OOM marker for the affected boot. No pending poweroff timer, scheduled shutdown record or matching readable system cron command was found. Power-only accessories, a case switch and an interrupted boot before journald starts need physical evidence. The board exposed `power_reset=0` under that name and did not expose the documented `reset_event` reason. The firmware reported `POWER_OFF_ON_HALT=0`. [Raspberry Pi power diagnostics and PMIC](https://www.raspberrypi.com/documentation/computers/raspberry-pi.html#power-supplies-and-raspberry-pi-os) · [Pi 5 power button](https://www.raspberrypi.com/documentation/computers/raspberry-pi.html#power-button)

The 17 November fix enabled the timer and moved its first verified alarm write to 4.680 s, before sysinit at 6.454 s. A controlled normal shutdown missed the 220-second observation window. The owner later reported an autonomous return, supported by the alarm and boot chronology. That test established delayed self-start under those conditions. It left recovery from repeated unstable boots and abrupt electrical loss open. The present incident supplies a concrete software failure at the final captured renewal. It does not identify the adapter, cable, controller, charging head or a particular reset source as the shutdown cause. ## Maintenance helper

The candidate renews a known owned future deadline with Linux’s in-place, relative `+=` form. It records pending ownership before touching the register, rechecks ownership after the durable state write and stops reading as soon as it observes the intended value. A transient empty or failed read can be followed by two more reads without reapplying the operation. If the replacement is lost and the slot is empty, it attempts to restore the previous verified, still-future deadline with an absolute write. The kernel rejects that write when another alarm already occupies the slot. A failed restoration or unknown future deadline remains visible in the private state and journal. Intentional disarm follows the same verification bounds and never rearms an alarm. The kernel sysfs interface offers no cross-process compare-and-swap against an unrelated privileged writer. [Helper](../../../../desk-companion/scripts/pi/auto_wake.py) · [Pi kernel wakealarm interface](https://github.com/raspberrypi/linux/blob/rpi-6.18.y/drivers/rtc/sysfs.c)

Using the incident timestamps and simulated hardware, the installed helper falsely failed after a single transient empty read and left the slot empty when the replacement was truly lost. The candidate accepted the correct later read in the first case and restored the verified 14:54:49 deadline in the second. The actual incident exposed no final register value to distinguish those possibilities. The local suite exercises transient reads, failed writes, foreign-alarm protection, persistent uncertainty, crash recovery, expiry and intentional disarm. Twenty-four focused policy tests passed on the Mac. The two Linux-only graph tests skipped on macOS. The original RTC service and timer files remained byte-identical. The local Linux VM’s systemd verifier accepted the shipped pair and detected the former ordering cycle when the old timer ordering was substituted. No deliberate shutdown or hardware alarm write was used to verify this candidate.

The investigation read the active project instructions, handoff, current product and Pi decisions, the 16–18 November recovery, wake, supply and cable evidence, and the installed timer/helper contracts. A pinned SSH session supplied bounded journal, unit, kernel, firmware and RTC read-only evidence. Private logs, full boot IDs, credentials and network identifiers remain outside the public report. The maintenance helper is pending independent source review and device deployment.
