# Group 2 · Recoverable retained-work maintenance

Date: 2026-10-13. Revised after independent design review. Status: **implementation proposal only**. No application changes, user-data deletion, filesystem cleanup, quota changes, migration, external calls, installation or publication were performed for this design. The current capacity batch remains independent and frozen. Current behavior is described in [capacity](../../desk-companion/docs/work-capacity.md), [files](../../desk-companion/docs/sources-and-artifacts.md), [runs](../../desk-companion/docs/agent-runs.md), [watches](../../desk-companion/docs/responsibilities.md), [search](../../desk-companion/docs/work-search.md) and [voice](../../desk-companion/docs/voice-work.md).

## Recommendation: finish one small recovery path first

Implement **terminal watch history → Trash → Restore or explicitly confirmed permanent removal → one recovered watch slot**, before extending maintenance to Work and immutable files. This is useful at the existing twenty-definition limit, has no filesystem/remote-effect transaction, and exercises the essential receipt/tombstone contract. It must not delete watched tasks or independently started Work. Do not create a general dependency engine, cold-storage service, new scheduler or automatic retention policy first.

The first slice includes a read-only impact preview, reversible terminal-watch trash/restore, fresh exact confirmation for permanent removal, atomic receipt-preserving removal, original-operation recovery and bilingual UI. Permanent removal is an application feature requiring its owner's explicit action-time confirmation; this design is not authorization to remove any current data. If implementing irreversible removal is outside the next batch's scope, ship preview/trash/restore honestly and leave capacity recovery marked unavailable. Merely shipping Trash is not quota recovery.

File and Work recovery below are a bounded next increment, not hidden acceptance requirements for the watch slice. Their first useful case is a terminal Work package with no unresolved child effect, followed by individually selected unreferenced source/artifact reservations. Unknown filesystem objects need a stricter later maintenance path.

## Four distinct meanings

- **Archive:** presentation organization only. Optional future label; no execution permission, content deletion or quota release. Do not add a separate archive state just to rename cancellation.
- **Trash:** reversible removal from ordinary selection/search; original records/bytes and receipts remain. No quota release. Restore makes the same record visible, preserving identity, terminal status, limits, spent budgets and history. Restore never resumes work or a watch.
- **Reclaim:** a measured accounting result after a successful approved removal, not a euphemism for deletion. Report logical reservations/bytes released separately from physical filesystem observations. SQLite page reuse does not mean the database file shrank.
- **Permanent removal/purge:** body/history removal that normal product recovery cannot undo. Separate fresh owner confirmation names exact records, dependent losses, independent records retained, and which integrity/dedupe metadata remains. No automatic empty-Trash timer. No claim about forensic erasure, backups, downloaded files, provider copies or already-completed external effects.

These meanings intentionally preserve today's `retained_reservations` basis: live + trashed + removal-pending bodies still consume their existing quota. Tombstones have a separate finite metadata budget. There is no second hidden trash byte allowance and no silent quota increase.

## Code observations driving the proposal

1. `ImmutableFiles.put()` in `backend/desk/file_store.py` stores `(kind, operation_key, request_hash)` in **the same `private_files` row** as the reservation. It looks up a prior key before count/byte checks, then reconciles the original ID. Deleting that row alone destroys the retry barrier and permits a fresh file effect under an old key.
2. The writer reserves SQLite first, creates `.<id>.pending`, fsyncs, hardlinks the final name, removes the temporary name, fsyncs the directory and independently reads final bytes. Crashes can leave no file, pending-only, final+pending hardlinks, or an unknown final file. Reconciliation never publishes a pending object and unknown reservations currently remain charged.
3. Source snapshots can retain `parent_artifact_id`; artifacts retain source provenance, `supersedes_id`, run/step association and byte evidence. Runs retain selected sources, observations, source coverage, output membership, pending decisions, effect/tool intents and child jobs. A filename or current output list alone is not a dependency inventory.
4. `AgentRunService.create()` looks up `agent_run_operations` before current scope and voice-draft admission. `agent_voice_origins` prevents a used draft producing another run under a new key. Removing either receipt/claim weakens that guarantee. Run actions also return current state from prior receipts.
5. A terminal run is not equivalent to immutable history: `steer` currently admits some terminal states. Any retention lifecycle must fence **all** actions, direct worker dispatch, proposal confirmation and late publication. `_authorize()` currently checks a changed generation only when a row exists; removal integration must explicitly reject missing/tombstoned runs before dispatch, not rely solely on the later publication checkpoint.
6. `agent_run_effect_intents` classifies run-owned proposals and guards actual confirmation. `_proposal_runs()` dereferences the parent. Removing the parent while dropping or leaving incompatible intent rows can remove access protection or break recovery. General `Store.operations` caches full request/response content, unlike hash-only run/watch receipts; it cannot be indiscriminately deleted or described as content-free.
7. Watches use four tables, foreign keys enabled by `Store.connection`, and same-transaction task/note triggers. A terminal watch no longer gets dirty markers; its Work-composer handoff is independent and has no durable exactly-one run link. `responsibility_operations` references definitions and possibly pruned review IDs. Deleting only the definition fails or damages replay.
8. Today's caps are source 100/64 MiB, Work 100, artifact 400/64 MiB, per-run artifact four/1 MiB, and watches twenty. All reservations/terminal rows count. Capacity and search each use a bounded complete corpus; simply leaving unlimited tombstones in their current scans breaks those assumptions.
9. There are prerequisite-before-receipt paths: `SourceService.from_artifact()` downloads the parent first, and `ArtifactService.publish()` validates sources/provenance/predecessor before `put()`. Removed dependencies must never make a retry fall through into a replacement operation.

These are inspected source behaviors, not new runtime test results. Relevant existing tests include `test_artifacts.py` crash/fsync/path/actual-process-exit cases and `test_work_capacity_admission.py` original-key recovery at full capacity.

## First slice: terminal watch lifecycle

### State and schema

Keep evaluation `status` independent from retention. Add `retention_state = retained | trashed | purged`, `retention_version`, and lifecycle timestamps to the definition. A purged row is a minimal tombstone shell rather than deleting the primary key. It keeps opaque ID, lifecycle version/state, terminal status/reason, receipt references and generation needed to reject stale operations. Remove title, selected task IDs/field hashes and review payloads only in the confirmed purge transaction. Do not expose its old title through a cached operation response.

The ordinary retained watch object remains backwards-compatible. A replay to a trashed/purged resource returns a discriminated `kind: "retention_disposition"` result containing only opaque responsibility ID, current retention state/version, original operation kind, optional opaque review ID, operation ID, workspace revision and `recorded_success: true`. This reports an already-recorded operation with the current disposition, not a new acknowledgment event or a fabricated full definition; do not set `acknowledged: true` as a newly achieved effect or embed removed labels. Normal detail and control endpoints reject the lifecycle state with a stable safe code; a dedicated owner-only maintenance detail can show Trash. Hidden mode continues existing stop controls only; maintenance and private history require a visible, current owner.

Add lifecycle operation kinds to the existing hash-only `responsibility_operations` rather than building a global ledger. Preserve each original key/hash/reference forever within the bounded store lifetime. After purge, review IDs remain opaque receipt references even when review bodies are gone; replay reports the historical operation and current `purged` disposition, not an inspectable acknowledged review.

### Bounds that survive repeated cleanup

Purging a twenty-slot definition permits replacement, which would otherwise make receipts grow without limit. Add a separate **256 lifetime watch identities** admission ceiling as an engineering proposal for this first slice (about twelve full replacements of the twenty-slot working set). Reserve that identity/tombstone slot at initial creation, not when the user is trying to clean up. Migrate existing definitions into these slots atomically; never discard legacy rows to fit. Existing corrupt/over-limit data must block new admission with a clear reason.

Preserve current **total receipt-count** semantics: creation, early pause/cancel, acknowledgment and lifecycle receipts all count together. New ordinary actions require total <256; there is no independently counted ordinary category. Creation consumes receipt 1 and a lifetime identity slot. Trash requires a terminal retained record and total <=254, then reaches at most255. While trashed only its Restore or final purge can create a receipt; Restore reaches at most256 and preserves terminality. Existing state-machine-valid final pause/cancel can reach at most258, and exactly one transition to purged adds at most one reserved final receipt: maximum259 per identity, or 66,304 for256 valid lifetime identities. The reserve is logical admission allowance, not preallocated disk space or a guarantee against disk-full errors; no separate reserve table is needed.

Original-key matching replays allocate zero. A new-key request to trash an already-trashed record, restore an already-retained record or purge an already-purged record is rejected with zero writes. Trash/restore cycles therefore consume budget and eventually stop, while every admitted Trash keeps one usable restoration slot. At the ceiling the owner can retain history or separately confirm direct terminal purge. Never label a nonrestorable move as Trash. Purge is permitted from retained-terminal or trashed state with the same fresh irreversible-action confirmation. Preserve and flag malformed/excess legacy receipt or identity counts; the proposed maximum is an admission invariant for valid state, not a claim that arbitrary preexisting corruption fits it.

Do not silently TTL-prune receipts, rotate operation namespaces, or clear the lifetime ceiling. A new creation is blocked when lifetime identity metadata is full, but original-key recovery, reads, stop and authorized terminal removal remain possible. This solves bounded repeated quota recovery, not infinite operation retention. A later versioned operation-epoch protocol can change that limit only with an explicit compatibility design; arbitrary current client keys cannot safely be forgotten.

### Eligibility and transaction

Preview accepts exactly one watch ID and current version; initial multi-select/bulk purge is out of scope. Only `cancelled`, `expired`, or `budget_exhausted` definitions may enter Trash or purge. Active/paused/blocked watches show “Cancel this watch first” using the existing control flow. Do not implicitly cancel on behalf of a maintenance action. No automatic task deletion or calendar/source selection occurs.

Preview returns exact affected counts (definition, source baselines, retained reviews), current necessary labels, expected logical slot release (zero for Trash; one for completed purge), retained opaque receipts and lifetime usage. It binds the exact requested action, ID, evaluation/lifecycle versions, canonical review/baseline inventory and real current owner session plus both settings.version and personal-settings epoch. A plain fingerprint is comparison metadata, never evidence of human consent.

Use one tiny watch-only process-local preview cache: at most32 opaque entries, each expiring five minutes after issue under both monotonic and wall-clock deadlines. Store only the bound IDs, versions, inventory digest, authority epochs and expiry; no title/body or full response cache. Return labels from the current DB. Eviction, expiry, restart and owner/privacy changes require a new preview and consume no durable receipt. The client cannot supply/extend expiry. No new scheduler or persistent credential is needed. This is read-only with respect to SQLite and user records, with bounded volatile metadata only.

A new mutation uses the current owner session, origin/anti-CSRF boundary, strict expected versions, original operation ID and server-issued preview ID. Purge additionally requires strict `confirm_permanent_removal: true`, sent only by the final owner click on its separate current confirmation screen; reject that field for nonpurge actions. An opaque preview reference or model/provider text alone is never consent. In one `BEGIN IMMEDIATE` transaction: check current visible-owner authority and durable historical receipt first; matching key/body returns the existing result without requiring an unexpired preview. Different body/target conflicts. For an unseen key, check cache expiry and exact action/session/epochs/inventory/versions again under the write lock, then terminal eligibility and total receipt budget; apply lifecycle changes, persist the receipt and bump workspace revision. New keys always require a fresh action-specific preview/confirmation. No cached confirmation authorizes a different operation.

Trash/restore only change lifecycle/version. Purge deletes `responsibility_sources` and `responsibility_reviews`, replaces definition content with a strictly validated tombstone, and leaves receipt rows referencing the same shell. Body removal, shell replacement, receipt and revision commit atomically. All count/replay/detail paths must understand the shell before enabling purge. The database write transaction serializes session/settings/privacy updates with maintenance; frontend event fences alone are not the authority boundary. Fresh owner/session/settings/personal-epoch response authority is checked after commit. A lost response can recover its exact original committed request under renewed authority even after preview expiry/restart; this is receipt recovery, not another purge. The UI clears old private queues on identity/privacy change and instead reopens current state as already specified.

Trash and restore preserve the original terminal status, expiry, nondecreasing day watermark and spent review budget. No evaluator or task trigger may select a trashed/purged identity even if legacy status is corrupt. Ordinary listing may omit Trash, but return a separately typed, validated `retained_count` aggregate including both retained and trashed rows and excluding completed purged shells. Also return bounded `trashed_count` where useful. Replace the current frontend's `responsibilities.length` quota calculation with that aggregate; a short visible list is never free capacity. Hidden stop listing receives the same content-free retained aggregate or explicit unknown, without calling the visible-only Work-capacity endpoint. Trash browsing contains at most twenty retained definitions; purged shells need only exact-ID/key lookup, not a new unbounded history browser. A new watch requires normal reviewed enrollment, new ID/key and a lifetime slot.

### HTTP/UI shape

Reuse `/api/responsibilities` with narrowly typed `/maintenance-preview` and `/{id}/retention` endpoints or equivalent small routes. Preview is read-only; retention actions are `trash`, `restore`, `purge` with strict fields. `purge` requires a separate confirmation screen and a fresh exact preview, never a checkbox bundled with “free space automatically.” The backend does not accept a provider/tool-callable purge path.

Use “Move to Trash / 移到废纸篓”, “Restore history / 恢复历史” and “Permanently remove / 永久移除”. Show “Trash still uses a saved-watch slot” and the exact remaining receipt metadata. Preserve drafts and stable unknown-operation retry keys within one valid privacy epoch. Identity/privacy changes clear private UI queues; reopening maintenance fetches actual state rather than generating a replacement operation. A cancelled confirmation has zero writes. Hide/show, session replacement, offline/stale state and reordered denials clear/disable the confirmation and fence old callbacks. The mutation success handler strictly decodes retained-result versus lifecycle-disposition. After trash/purge it clears selected ordinary detail before refresh, so a rejected ordinary detail inside the current parallel refresh cannot blank the whole workspace. Trash uses explicit maintenance detail, never an incomplete `WatchDetail`. Refresh authoritative retained usage. Do not mark the watched task complete or imply that “seen” reviews were actually read by a person.

## Extension: Work, source and artifact maintenance

Do this only after the watch slice independently passes. Reuse the lifecycle vocabulary and response union, but not a generic cascade-delete implementation.

### Dependency rules, deliberately conservative

- **Work:** require terminal, no running attempt/lease, no pending effect/tool decision, and no unknown external outcome or unconfirmed process cleanup. A cancelled parent alone does not prove children settled. Discover child references from persistent intents and child receipts as well as linked arrays, covering reserve→dispatch→link crashes. Read-only reconciliation is allowed only through existing authorized services; never redispatch an uncertain write to make it removable.
- Work removal does not remove tasks/calendar changes, child application records, independent files, provider accounting or voice-origin claims. Keep intent ownership classification and immutable child-operation hashes in content-free parent tombstones. Guard helpers must treat a purged parent as a permanently closed authority, not as an unrelated legacy proposal. Outstanding unconfirmed proposals must already be closed before purge.
- **Source:** first release only records with no referencing nonpurged Work, artifact provenance or remaining source-coverage dependency. Trashed dependents also count. Explain blockers as exact selectable records; no silent cascade. An independently retained derived artifact must not lose promised inspectable evidence without its own reviewed action.
- **Artifact:** first release only when not referenced by nonpurged Work output/history, another artifact's `supersedes_id`, or a source's `parent_artifact_id`. Do not use only `current_artifact_ids`. Purge dependent Work metadata first while retaining its files; then newer artifacts before predecessors and source snapshots before parent artifacts where applicable.
- If conservative edges create a cycle (for example a run reads a source derived from its own prior output), refuse single-item purge and show the exact cycle. An explicitly reviewed bounded package removal can be a later increment. Do not silently broaden today's preview into recursive deletion.
- Malformed/missing relation metadata means dependency status unknown, not no dependencies. Block destructive mutation without guessing. Dependency checking uses bounded validated projections and rechecks under final write lock; a source selection/publication must also acquire/check that same lifecycle fence, closing the preview-to-new-reference race.

Trashed sources/artifacts cannot be selected by a new run, previewed/downloaded through ordinary endpoints or cited by a new publication. Trash preview can offer explicit same-ID restoration; restoration does not approve model transmission. Initially refuse to trash referenced files, avoiding broken existing run details. A trashed Work is terminal and cannot steer/resume/confirm; restore does not reauthorize it.

### Durable receipts before releasing live rows

Use minimal per-domain tombstone shells or dedicated receipt tables, not absence as success. File tombstones retain authoritative SQL kind/ID, original operation key/hash, lifecycle state/version and safe outcome time; no body/display name. Separate them from the active `private_files` reservation scans using explicit indexed lifecycle predicates. The original key must be checked across both live/tombstone states before any capacity decision or dependency loading.

New file commands should store a versioned **input intent fingerprint** computed before source/predecessor reads, alongside the existing resolved publication fingerprint. It binds the exact request, selected IDs, trusted run/step origin and content digest without storing content. `from_artifact` needs its own exact parent-ID intent lookup before downloading its dependency. Matching original intent can return a trashed/purged disposition; changed intent conflicts. Never revive the body as part of retry.

Legacy file receipts lack that separate input fingerprint. Do not invent one from unavailable historical dependencies. Safest compatible behavior for a retired legacy key is unconditional `OPERATION_RESOURCE_REMOVED` with the opaque former ID; it must never execute, even if the supplied body changed. Document that this terminal response cannot distinguish identical from changed legacy bodies. For retained records preserve today's resolved-hash conflict checks. Run/watch existing request hashes remain directly comparable, so those replays continue distinguishing wrong-body conflicts.

Keep `agent_voice_origins` claims after Work purge. Used voice input stays used under a different key; original create reports the run's terminal removal instead of consulting expired volatile drafts. Same operation never implicitly restores a record. A new deliberate re-upload may create a new independent source under a new key and current consent; it is not described as recovery of the old effect.

Per-run artifact accounting is a lifetime-attempt bound, not merely currently present output. Purging an artifact must not reset its parent's four-reservation/1 MiB history or permit replacement under stable revision/index keys. Preserve a compact per-run publication ledger until that run itself is irreversibly retired, and reject further effects from retired parents regardless of newly available global capacity.

### Filesystem reclaim protocol (later, separately tested)

Retain content in place while merely trashed; this avoids a second copy, path migration and restore race. Permanent removal is an intent-based local protocol, never `rmtree`, arbitrary paths or a directory sweep.

1. Exact preview inventories DB reservation and code-derived final/pending names, current safe identity, byte/digest facts, dependency closure and publisher quiescence. Only generated IDs and fixed extensions are admissible. Do not accept a model/client path.
2. After fresh owner confirmation, atomically persist a `purge_pending` tombstone/intent and increment lifecycle generation. Original publishers/reconcilers/checkers must recheck that generation before final link, status update or response. A late `_status(verified)` may not revive a purged row. New source reads/publications are blocked.
3. Hold an in-process per-file lifecycle lock across the admitted filesystem phase; all file publication/read/reconciliation paths must join that lock in one documented order. Do not hold the global privacy lock or a SQLite write transaction across byte I/O. Existing single-host/API assumption remains explicit.
4. Open trusted private directories with no-follow descriptors, match exact inode/dev/type/owner/mode/link count and expected names, then unlink only admitted objects; fsync the directory. A legitimate final+pending pair sharing the expected inode needs a specifically verified two-link case. Refuse unknown extra links, substituted files, symlinks, wrong ownership or unsafe modes. Crash evidence is not permission to delete a suspicious object.
5. When each selected path is absent and durability is established, finalize tombstone and release logical reservation in SQLite. A lost reply uses the original purge operation. Crash after intent resumes **only this already-authorized cleanup intent**, never original publication. No directory sweep on restart. Recovery revalidates target identity; changed targets block rather than widening approval.
6. Missing-before-purge and actually-unlinked bytes are distinct outcomes. A failed unlink/fsync or uncertain storage state keeps `purge_pending` charged; display blocked cleanup and retained quota. Do not infer successful physical reclamation from a SQLite row disappearing.

Initial file-purge implementation should admit verified, quiescent, unreferenced finals and proven-absent reservations only. Pending-only partial data, unexpected hardlinks, opaque unknown bytes and live publishers stay blocked until their exact identity/recovery protocol is implemented. A whole-disk-full error can prevent even durable cleanup intent creation; report that verified storage blocker rather than promising cleanup always works. Application quota-full is different and must not block maintenance intent admission.

## How full quotas recover, without resurrection

- Twenty saved watches → cancel an eligible watch explicitly → Trash (still twenty) → restore (still twenty) **or** confirm purge → nineteen retained plus one tombstone → create one normal new watch if lifetime metadata admits it. Replay old create/control/purge reports the old ID's current tombstone. It never inserts a new definition, resets budget or acknowledges a new review.
- One hundred Work rows → no relief from cancel/archive/trash → approved eligible Work body removal releases one retained-run slot, while creation/control/voice/effect barriers survive. This path is later, not provided by watch cleanup.
- Full source/artifact count or byte bucket → no relief from moving to Trash or downloading → dependency-safe, confirmed file purge → release exact logical count/recorded bytes only after durable outcome. Unknown pending cleanup stays charged. Historical per-run attempts remain spent.
- Full receipt/tombstone identity budget → no unbounded new creation. Existing receipt recovery and final maintenance stay available because their storage was reserved when admitting each resource. No claim of endless cleanup/recreation at fixed metadata size.

Capacity v1 must continue its exact existing contract during watch-only development. Once lifecycle is enabled, update the shared admission predicate and capacity query together: for the watch-only slice retained means `retained` plus `trashed`, excluding only completed `purged` shells. Watches need no `purge_pending` state because their mutation is one SQLite transaction. Later file retention additionally charges `purge_pending`. Add a separately versioned maintenance-usage response for Trash/pending/tombstone counts and lifetime headroom; do not add incompatible keys to today's exact response accidentally. `basis` documentation must specify body reservations and separate receipts. Query limit+one over the indexed retained predicate, so tombstones cannot cause false over-limit. Watch cleanup does not expand general Work search, which currently contains no watches. Use the existing watch workspace and bounded Trash view. The later Work/file extension must exclude Trash from normal search, bind pagination to lifecycle changes, and show missing old links as removed/unknown rather than invented provenance.

## Implementation and release gates

First batch touches responsibility lifecycle/schema/replay, owner routes, watch UI/types, shared watch count predicate/capacity, focused tests and the minimal Store bootstrap/migration compatibility seam described below. No source/file/run mutation endpoints, global search expansion, general service factory or automatic cleanup thread. Use explicit column INSERTs, indexed retained predicates, validated body/tombstone decoding and positive retention gates in worker, expiry, triggers, ordinary actions, acknowledgment, detail and replay.

### Migration and truthful downgrade contract

Current `Store.__init__` unconditionally writes `PRAGMA user_version=1`; a new version check cannot retroactively stop that already-shipped binary. The independent review actually reopened a synthetic version2 store with the old Store and observed it reset to1. Therefore require an **operational no-downgrade contract**: stop the single API process and every worker, make and verify a coherent protected pre-migration SQLite backup (including committed WAL state through SQLite's supported backup mechanism), and migrate only using the supported new binary. Do not let older binaries open the migrated store. This is an operator/deployment requirement, not an automatically enforced property of an additive schema migration. Strong enforcement against historical binaries would require a separate proven launcher/storage-isolation design, which is out of this slice.

New supported binaries must read schema/version compatibility before any bootstrap DDL, settings writes or version assignment, and reject unsupported forward schemas. Remove the unconditional version reset from that supported startup path. This protects future cooperating binaries only. It does not alter credentials or security permissions.

Migrate using individual `execute` statements inside one explicit `BEGIN IMMEDIATE`, with schema validation before service bootstrap. The current `executescript()` pattern commits an existing transaction first; merely wrapping it in `Store.connection(write=True)` is not atomic. Column additions, validated transformed rows, required indexes, lifecycle-aware trigger replacement and the new version commit together or all roll back. Explicitly drop/recreate the changed known task/note triggers inside that transaction: `CREATE TRIGGER IF NOT EXISTS` would retain their old bodies. No migration may delete existing IDs, receipt hashes, tasks or history to fit a limit. Preserve invalid/over-limit state and stop new admission with a diagnosable error.

Verify the backup is readable and coherent in an isolated location before migration, and run crash/rollback checks with synthetic stores first. An intentional rollback uses an isolated pre-migration backup and explicitly acknowledges loss of post-backup changes; never silently restore purged data or replay old effects. A backup still contains pre-purge history until the owner's separate backup handling removes it. Purge claims exclude that backup. No backup, migration, deployment or rollback is executed by this design.

Required automated tests use isolated real SQLite and fixture files, never user runtime data:

1. Exact watch-capacity end-to-end example above; new creation is refused before actual purge, succeeds afterward, and only one slot is released under concurrent identical purge retries.
2. Rollback/process-exit before/after mutation commit and lost-response retry; body removal and receipt/barrier cannot commit separately. Same-key changed bodies conflict for watch/run commands.
3. Purged creation/control/acknowledgment replay returns safe disposition after restart/expired scope/review pruning. An old key with changed target cannot operate on another record. No retained response leaks an old title.
4. Cancel/expiry/evaluator interleavings, paused/blocked eligibility refusal, late task trigger/evaluation, and restore preserve terminality, original budgets and no pending alert.
5. Retained-watch versus visible-list usage, lifetime identity and all-receipt bounds, exact Trash totals254/255 and Restore256, stop/purge maximum259, distinct-key no-op refusals, and reserved restore behavior; malformed/excess legacy state is preserved and cannot appear as free space.
6. Preview eviction/dual-clock expiry/restart, action/ID/inventory/version/session/settings/personal-epoch mismatch, no cached confirmation reuse, and committed same-key recovery after preview loss. Authenticated owner only; paired/device/forged owner rejected; hide→show/logout/offline/stale/late success and denial invalidate maintenance preview/confirmation. A postcommit authority denial does not cause a new operation on retry.
7. Existing task/event/file/run/voice data and hashes unchanged by watch purge; composer-created Work remains independently inspectable. No provider/network/OS permissions accessed.
8. Bilingual screen has exact counts, Trash-not-reclaim warning, strict final-click permanent confirmation, cancel-with-zero-effects, current tombstone result, post-removal selected-detail clearing and no automatic emptying. Actual mounted desktop/narrow-screen acceptance is separate from callback/SSR tests.
9. Migration rollback and child-process exit after every schema/row/trigger/version step; forward-schema refusal before bootstrap; known trigger bodies actually replaced; old Store behavior documented without claiming it is prevented. Backup integrity and intentional rollback procedures are verified independently before any real migration.

Before later file/Work release, additionally require crash injection at every reservation/intent/link/unlink/fsync/finalize point, child-process exit, concurrent read/download/publication/removal, legitimate two-link residue and malicious link/identity substitution, unlinked child intent detection, unknown remote-effect blockade, publication generation races, dependency creation during preview, per-run lifetime counters, voice-origin replay, malformed graph/cycle refusal, metadata-full reserve behavior and exact zero writes on rejected approval. Recompute real remaining file bytes; do not substitute UI text for evidence.

## Completion boundary

This proposal incorporates the [independent review](../../output/qa/2026-10-13-terminal-watch-retention-audit/review.md) and is finalized as a design, not accepted implementation.
